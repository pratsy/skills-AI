# Public Repo Guidelines

## Public vs private separation

The public GitHub repos should feel curated, polished, and operationally useful.

### Public content

Public content should include:

- final playbooks
- structured prompts
- example outputs
- evaluation rubrics
- source references
- business framing
- well-defined use cases

### Private content

Keep in private notes or a private repo:

- daily planning
- brainstorming notes
- internal debate
- raw prompt drafts
- failed experiments
- release planning
- internal task calendars
- rough research ideas

## What to publish

Each published skill should include:

- name
- problem it solves
- use case
- inputs
- outputs
- workflow
- prompt template
- example result
- scoring rubric
- source references

## What not to publish

Avoid publishing:

- daily plan documents
- prompt iteration logs
- unfinished drafts
- private commentary
- poorly structured experiments
- references to internal planning or workflow chatter

## Framing language

Use language such as:

- research-informed
- practitioner-informed
- operationally grounded
- curated skill library
- business-first GTM playbooks
- synthesized from field practice and public frameworks

Avoid language such as:

- AI-generated by Claude
- raw LLM output
- daily prompt dump
- rough experimentation log

## Sources and transparency

Every skill should include a `sources.md` or source section with a short list of references. The material should be framed as a synthesis of:

- practitioner workflows
- known B2B sales and marketing frameworks
- revenue operations playbooks
- public market research and strategic references

This makes the project feel credible without pretending to be a single vendor or expert authority.
